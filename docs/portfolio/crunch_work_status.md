# Crunch 작업 상태 (2026-10-08 기준)

기획서(`crunch_ai_design_doc.html`)에는 의도와 설계만 둔다. 진행 상황, 할 일, 도구 사용법은 여기에 적는다.
자세한 작업 기록과 실측은 `crunch_punch_polish_20261008.md`.

## 끝난 것
- 중거리 버전 모션: 1번 왼손, 2번 오른손, 3번 어퍼컷(더킹), 5번 잽잽훅. 제작 `Tools/AuthorCrunchRunIn.py`.
- 거리별 전진량 조절(`UpdateTravelScale`, 타마다 멈출 거리는 애니메이션의 `TravelStop` 커브: 300 / 280 / 255 / 210cm).
- 중거리 달려오기(`FinalizeWeights`: 345cm 이상에서 접근을 공격 점수 합의 35%까지 남김). 자동 시험 12개 통과.
- 훅 단독 카드(모션랩 K키, 측정용). 훅은 5번 마무리 전용으로 결정.
- 모션랩: L 두 번 → 1 / 2 / 3 / 5가 중거리 버전. K 훅 단독, J 사거리 측정, H 타격 구.

## 사용자 QA 결과
- 1·2번 두 걸음 진입: "아주 좋아". 전체: "일단 이거로 가자". 3번 덜커덩: 해결 확인.
- 실측 사거리: 단거리 버전 1번 344 / 2번 330 / 3번 323 / 4번 423 / 6번 337 / 훅 238cm. 중거리 버전 1번 523 / 2번 539 / 3번 599cm.

## 확인이 필요한 것
- 달려오기 빈도(35%, 345cm)는 첫 값. Arena에서 봐야 한다. 모션랩에서는 볼 수 없다.
- 멈출 거리 300 / 280 / 255 / 210cm는 첫 값.
- 5번 판정 규칙: 단거리 공격으로 두고 중거리 버전은 시작 거리로 한 번만 고르는 안(추천) vs 타 사이에 멀면 생략하는 안. 미결.
- 기획서의 "(확인 필요)" 표시된 의도들: 사용자에게 질문 중.

## 남은 일
- 실전(Arena) 연결: 중거리 버전은 아직 모션랩에서만 재생된다. 1·2·3·5번 카드를 단거리 / 중거리 버전으로 나누고 시작 거리로 고르게 한다.
- 실전 카드의 최대 거리를 실측에 맞추기(4번 285 → 423, 6번 285 → 337, 3번 250 → 323 등).
- 옛 전진 카드 4개(`DA_Attack_Advance*`)를 계속 쓸지 결정.
- 포트폴리오용: 패턴 대응표(예고 / 피하는 법 / 반격 시간), 밸런스 표, 실전 영상.
- 커밋: 2026-10-07 이후 작업(애니메이션, 코드, 문서)은 전부 미커밋.

## 주의
- 사용자가 플레이 중이면(PIE) 에셋 작업과 빌드를 할 수 없다. 두 번 플레이를 직접 종료했다.
- 미커밋으로 남아 있는 Codex의 `Tools/AuthorCrunch510Punches.py`, `TestCrunch510Punches.py`는 건드리지 않았다.

  돌 때 발은 그대로라 제자리에서 미끄러지듯 돈다(턴 동작 없음). 사용자 QA 필요. 0.5와 60은 첫 값.

  230cm 안이면 훅 / 휩쓸기 반반, 그보다 멀면 휩쓸기. 쿨다운 6초. 준비 동작 동안 초당 300°로 돈다. 훅 카드는 `DA_Attack_Hook`(왼손 자리로 요청하고 카드만 바꿈).
- **시험 4회**(왼손 뒤 플레이어를 등 뒤로 옮김): 훅 명중(65) 1회, 휩쓸기 명중(160) 2회, 대응 없음 1회(확률). 자동 시험 `Battle.Boss.RearResponse`.
- 공격이 끝난 직후에만 발동한다. 평소 Ready에서 뒤를 잡힌 경우는 예전처럼 턴 동작이다.
- 60% / 6초 / 300°는 첫 값. Arena에서 사용자 QA 필요. 모션랩에서도 플레이어가 뒤에 있으면 발동한다.
- 기획서 방침(사용자): 군다 언급은 넣지 않는다("베꼈다"로 읽힐 수 있음). 구현 과정의 문제(예: 어퍼컷 덜커덩)는 넣지 않는다. 기획자가 쓰는 문서로 생각할 것.
- 기획서에 Utility 시각화 추가: 거리 축 위의 카드 막대, 거리별 뽑힐 비율.
- 시험 주의: PIE에서 컴포넌트에 `set_editor_property`를 쓰면 보스가 다시 생성되어 Dead가 된다.

## 2026-10-08 밤 2: 달리기와 회전 다듬기 (사용자: "달려오기 더 빠르게, 걷기는 Jog 달리기는 Sprint", "뒤로 갈 때 어색하게 돈다, 알아서 폴리싱")
- **Sprint**: `UpdateSprint`. 속도 520 이상이면 전신 Sprint 몽타주(`AM_Crunch_SprintLoop`, `Sprint_Fwd` 복제 + FullBody 커브, 반복)를 재생, 430 미만이면 뺀다. 재생 속도 = 실제 속도 ÷ (686 × 배율).
  달려오기 최고 속도 440 → 760(블루프린트의 `ApproachRunSpeed`를 실행 중에 덮어씀), 자리 잡기 `RunSpeed` 600 → 760.
  Arena 실측(1200cm에서 시작): Jog로 출발 → 570cm/s에서 Sprint → 최고 760 → 327cm에서 오른손. AnimBP와 블렌드스페이스는 건드리지 않았다.
- **후딜 회전 방식 변경**: 발을 둔 채 도는 것(초당 60°)을 껐다(`RecoveryTurnSpeed` 0). 대신 후딜 60%에서 플레이어가 60° 이상 옆·뒤면 후딜을 일찍 끝낸다(`FlankExitFraction`, `FlankExitAngle`).
  실측: 왼손 후딜 2.2초 → 옆·뒤를 잡히면 1.3초에 끝남. 정면이면 그대로.
- **턴 동작 맞추기**: `UpdateTurnSync`. 턴 몽타주(90°: 1.5초, 180°: 2.5~3초)를 각도 ÷ 130°/s 길이로 재생하고 블루프린트의 `TurnSpeed`, `TurnAnimationUntil`을 같은 시간에 맞춘다(끝나면 원래 값).
  실측: 90° 턴이 0.85초에 끝나고 그 순간 정확히 90° 돌아 있었다.
- **뒤쪽 대응 회전**: 고정 300°/s 대신 "타격 0.15초 전에 정면"이 되는 속도로 고르게 돈다. 실측 3회 모두 명중(훅 1, 휩쓸기 2).
- 컴포넌트를 첫 Utility 판단 때 만들도록 했다(`FinalizeIntentScores`). 전에는 첫 공격 뒤에야 생겼다.
- 시험: `Tools/TestBossSprint.py`(Arena), `TestMidrangeAudit.rear_response_scenario`. 자동 시험 추가분 포함 통과 여부는 빌드만 확인, 실행은 다음에.
- 사용자 QA 필요: Sprint로 바뀌는 순간의 이음, 일찍 끝나는 후딜의 느낌, 턴 속도(130°/s), 돌아서며 치는 모습. 숫자는 전부 첫 값.
- 모션랩의 8키(접근)는 시험 스크립트에서 움직이지 않았다(원인 미확인). Sprint는 Arena에서 확인했다.

## 2026-10-08 밤 3: Utility 점수 다듬기 (사용자: "제안대로 다 고쳐줘, 기획서에 쉽고 상세하게")
- **발견: 추첨이 아니라 최고점 선택이었다.** 블루프린트 `ChooseCombatAction`이 누적 추첨 대신 가장 큰 점수를 골랐다(`UtilityRoll`은 계산만 하고 미사용).
  실전 23회 기록이 "왼손 → 오른손 → 어퍼컷/2연타"의 3박자로 똑같이 반복됐고 휩쓸기·연속기는 0회였다.
  수정: `FinalizeIntentScores`에서 점수 비율대로 추첨(`WeightedPick`)하고, 당첨 카드의 점수만 그 순간 최고로 만들어 블루프린트가 고르게 한다. 표시용 점수는 다음 Tick에 원래대로(`RestoreTrueWeights`). 블루프린트 그래프는 건드리지 않았다.
- **감점**: 블루프린트의 세 배수를 실행 중에 1로 두고(`UtilityRepeatMultiplier`, `RecentUseMinMultiplier`, `PunchFamilyMinMultiplier`), `AdjustIntentCandidate`가 가장 큰 감점 하나만 적용(`StrongestPenalty`: 연속 0.5 / 최근 0.35→12초 / 주먹 계열 0.55→6초).
  "쓴 시각"은 블루프린트가 그 공격이 끝날 때 찍는다(`CooldownUntil`). 블루프린트의 "쓴 지 얼마 안 됨" 배수는 실측에서 점수에 반영되지 않아 손대지 않았다(처음에 그걸 되돌리는 보정을 넣었다가 감점이 반만 걸려서 뺐다).
- **가중치**(카드 에셋): 왼손 28→30, 오른손 28→24, 어퍼컷 30→16, 2연타 20→18, 휩쓸기 30→12. 연속기·가드 브레이크·슈퍼맨·점프·접근은 그대로.
- **연속기 기본 점수**: 회피를 못 봐도 기본 가중치의 30%(12). **휩쓸기**: 최근 회피 2회 이상이면 3배. **달려오기**: 플레이어가 초당 150cm 이상 물러나는 중이면 몫 35% → 70%.
- **실전 실측**(Arena, 서 있는 플레이어, 2초마다 체력 회복): 45회 중 왼손 13 / 2연타 8 / 휩쓸기 7 / 어퍼컷 7 / 오른손 7 / 연속기 3, 연속 반복 1회. 다른 31회 기록은 반복 7회(왼손 4연속 포함).
- 자동 시험 `Battle.Boss.UtilityPenalty` 추가(전체 16개는 빌드만 확인, 마지막 실행은 15개 통과 시점).
- 사용자 QA 필요: 휩쓸기가 평소 16%로 "드물다"보다는 자주 나온다(감점을 안 받는 유일한 일반 후보라서). 회피·가드하는 플레이어 상대 빈도는 재지 않았다. 가드 브레이크는 추첨이 되어 가드 중에도 확정이 아니다.
- 시험 도구: `Tools/TestBossSprint.py`의 `long_scenario`, `probe`.

## 2026-10-08 밤 4: 공격 뒤 발놀림 (사용자: "붙으면 목석처럼 공격만 한다, GOAP 알아서 폴리싱")
- **원인**: 후딜이 끝나는 프레임에 바로 다음 공격을 골랐고, 가까우면 이미 칠 수 있는 거리라 Position에서 할 일이 없었다. 사용자 플레이 기록에서 붙어 있는 표본 615개 중 614개가 정지.
  블루프린트의 옛 간격 기능(`UpdateCombatSpacing`, 160cm 미만에서 발동)은 몸이 닿는 거리가 172cm라 한 번도 발동하지 않는다. 손대지 않았다.
- **구현**(코드만, 블루프린트 그래프 그대로): `TryFootwork` / `TickFootwork` / `EndFootwork`(`BossCombatIntentComponent`), 계획 `UBossPositionPlanner::PlanFootwork`(`BossAttackPositionPlanner.cpp`).
  후딜 끝(`RecordAttackRecoveryEnd`)에서 뒤쪽 대응 다음에 판정 → Ready → Position → 한 걸음 → Ready. 모션랩 맵에서는 하지 않는다.
- **언제**: 발 안 옮기고 친 공격 수 1 / 2 / 3+ → 25 / 55 / 85%, 붙어 있으면(200cm 미만) +20%p, 최대 90%, 2페이즈 ×0.7. 치러 120cm 이상 걸어 들어가면 수를 0으로.
  안 하는 때: 가드 2초 이상, 플레이어가 옆·뒤(dot < 0.5), 420cm 초과, 쓰러짐, 2페이즈 첫 점프 대기.
- **어떻게**: 사실 3개(간격 / 정면 / 각). 뒤로 한 걸음(간격 260cm까지, 210cm/s), 옆으로 30°(240cm/s). 붙어 있을 때 65%는 "간격 + 각" 목표. 좌우는 플레이어 옆 이동 방향(±80cm/s 이상) 쪽, 아니면 무작위. 최대 1.3초.
- **같이 바꾼 것**: `PostAttackProbeChance` 0.25 → 0(고른 뒤 옆걸음: 발놀림이 대신함). 어퍼컷 카드 `MaxDistance` 250 → 285(발놀림 뒤 거리 245~260에서 후보에서 빠져 2%까지 떨어졌다. 실측 사거리는 323).
- **실측**(Arena, 서 있는 플레이어, 307초, 1.5초마다 체력 회복): 공격 66회 = 왼손 21 / 오른손 16 / 어퍼컷 8 / 2연타 8 / 연속기 8 / 휩쓸기 5, 연속 반복 6회.
  발놀림 35회(뒤 18: 0.48초·63cm, 옆 17: 0.71초·120cm·27°), 발놀림 사이 공격 1번 12 / 2번 16 / 3번 7. 걷는 중 정면 오차 최대 20°.
- 자동 시험 17개 통과(`Battle.GOAP.Footwork`, `Battle.Boss.Footwork` 추가).
- 사용자 QA 필요: 걸음이 자연스러운가(210 / 240cm/s로 Jog 블렌드를 느리게 재생), 발놀림 직후 멈춤 없이 바로 공격으로 넘어가는 모습, 빈도(붙으면 공격 2번에 1번꼴), 뒤로 63cm가 너무 작은지. 숫자는 전부 첫 값.
- 재지 않은 것: 움직이는 플레이어(좌우 선택), 벽 근처(뒤가 막혀 옆으로 빠지는 경우), 2페이즈. 계획 자체는 자동 시험으로만 확인.
- 시험 주의: `long_scenario`는 1.5초마다 회복해야 한다(5초면 플레이어가 죽고 보스가 Ready에서 멈춘다). 에디터를 새로 연 직후 첫 시나리오는 플레이어를 못 찾아 실패한다(PIE를 한 번 켰다 끄면 된다).
- 기획서: GOAP 절을 "① 칠 자리 만들기 / ② 공격 뒤 발놀림"으로 다시 씀. Utility 절의 전후 비교표를 "실전 측정"(지금 것만)으로 바꿈.

- **거리 구간 제거**: `MidRangeEnd` → `MaxRunInReach`(모션의 한계). 달려오기의 몫은 거리 구간이 아니라 닿는 공격 수로(`ApproachShare`: 1개 1.5 / 2개 0.5 / 3개 이상 0.15, 제자리 공격이 닿으면 0, 물러나면 2배). `FinalizeWeights` 시그니처 변경. 화면: "닿는 공격 N개", 예상 거리, "(달려)".
  `PlayLog.py`의 구간 집계는 측정용으로 남김.
- **닫힌/열린 후딜**(`bRecoveryOpen`, `RecoveryLabel`): `UpdateRecoveryTurn`에서 닫힌 동안은 연계·추격·옆뒤 대응 코드에 닿지 않는다(35%에서 열림, QA `recovery_open`). 블루프린트의 상태 태그는 그대로 `Attack.Recovery` 하나이고, 하위 상태는 컴포넌트가 갖는다.
- **전후 비교 스위치**: 콘솔 `boss.LeadTrust 0`, `boss.OutcomeMemory 0`. 시험 `TestBossSprint.retreat_scenario(seconds, lead, memory)`(실제로 걷는 플레이어).
