# 공격 의도를 유지하는 Crunch — 구현 진행 기록

## 원했던 경험

굼뜨지만 연속으로 압박하는 기계 복서. 조금 떨어진 플레이어에게 공격할 생각으로
진입하고, 발과 몸을 실어 공격한다. 무조건 명중시키는 것이 아니라 플레이어가
공격 종류와 타이밍을 읽고 대응하게 만든다. 마지막 후딜에는 반격 기회를 준다.

## 왜 바꾸는가

기존에는 접근을 선택하고 도착한 뒤 다시 공격을 골랐다. 그래서 공격 의도가
이어지지 않고 추격을 반복할 수 있었다. 기본 주먹을 선택할 수 있는 350cm도
실제로 주먹이 닿는 범위라는 보장이 없었다.

추가로 `FinishCombatAction → TryBeginFollowup` 경로는 마지막 후딜이 끝난 뒤
35% 확률로 기본 공격을 다시 시작했다. 이 경로의 일반 펀치는 거리·쿨다운을
검사하지 않았다. 최근 로그에서 별도 선택 기록 없이 멀리서 펀치를 시작한
현상과 일치하지만, 예전 로그에는 호출 경로가 없어 모든 사례의 원인이라고
단정하지 않는다.

## 적용한 것: 1단계

- 마지막 후딜 뒤 무작위 추가 공격의 실행 연결을 끊었다. 기존 함수는 비교와
  복구를 위해 보존했다. 앞으로 추가할 2연타는 처음부터 선택한 하나의 패턴이다.
- 공격 시작 전에 공통 검사 `ValidateCombatActionStart`를 거친다.
  대기 상태 → 공격 데이터와 대상 유효성 → 대상 생존·넘어짐 → 사용 가능 여부
  → 공격 모션 → 쿨다운 배열 인덱스 → 쿨다운 → 거리 → 방향 순서로 확인한다.
- 검사가 끝나기 전에는 공격 상태·이동·판정 식별자를 변경하지 않는다.
  사거리·각도는 현재 공격 데이터와 정면 60도 기준을 사용한다.
- 페이즈 2 첫 점프 공격은 요청 출처가 `phase_intro`이고 행동 ID가 8일 때만
  거리·방향·쿨다운 예외를 적용한다. 상태·대상·모션 검사는 유지한다.
- 자동 선택(`utility`), 일반 수동 요청(`manual`), 페이즈 시작(`phase_intro`)을
  기록한다. 공격 시작이 허용되면 실제 행동 ID·이름·몽타주·거리·방향을 보관한다.
- 로그 분석은 이전 선택 문구를 실제 공격 이름으로 사용하지 않는다.
  옛 로그는 슬롯만 표시하고, 새 로그는 시작 시 보관한 행동 이름을 사용한다.
  `attack_accepted`는 요청 허용, `state ... Windup`은 공격 준비 진입으로 구분한다.

이 단계는 추격 방식을 개선한 단계가 아니다. 잘못된 공격 실행을 막고, 다음
개선을 정확히 판단할 수 있게 만든 기반 작업이다.

## 검증

- 보스 블루프린트 컴파일 오류 0, 경고 0.
- 저장 후 그래프를 다시 읽어 시작 검사 선행, 11개 순차 검사, 쿨다운 인덱스 연결,
  이전 추가 공격 함수의 실행 호출이 없는 것을 확인한다.
- 로그 분석 테스트 7개 통과: 오래된 선택 이름, 거부된 요청, 실제 공격 시작,
  세션 분리, 접촉과 피해 구분 등을 검증한다.
- PIE·플레이 화면 확인은 하지 않았다. 자연스러움과 실제 팔 접촉은 미검증이다.
- MotionLab 숫자키 실전 요청에도 이제 일반 검사가 적용된다. 사거리 밖이거나
  쿨다운 중인 요청은 거부될 수 있다. O키의 원본 모션 관찰 기능과는 별개다.
  실전 요청 거부 이유를 랩 화면에 표시하는 후속 작업이 남았다.

## 적용한 것: 2단계 — 선택한 공격으로 진입

기본 왼손·오른손은 650cm까지 **짧게 진입해서 사용할 후보**가 된다. 주먹 자체의
시작 허용 상한은 350cm로 유지한다. 650cm에서 팔 판정을 늘려 때리는 방식이 아니다.

Utility가 공격을 선택하면 `Boss.Combat.Position` 상태로 들어간다. 이 상태에서는
기존 Ready 전용 선택기가 다시 공격을 추첨하지 않는다. 선택된 공격 데이터와 슬롯을
보관하고, 선택이 외부에서 변경되면 현재 진입은 중단한다.

- 최대 2초 동안 공격 시작 위치를 준비한다. 0.2초마다 상대 위치를 다시 보되
  제한 시간의 시작 시각은 갱신하지 않는다. 진입 최고속도는 600cm/s다.
- 처음부터 시작 범위에 있다면 불필요하게 물러나지 않고 공격 시작 검사를 거친다.
  진입이 필요했다면 상한보다 40cm 안쪽을 목표로 삼아 경계에서 멈추는 현상을 줄인다.
- GOAP은 선택한 공격의 거리·방향 조건을 받는다. 이미 조건이 맞으면 추가 행동이 없고,
  멀면 진입, 너무 가까우면 후퇴, 방향이 어긋나면 회전을 계획한다. 이동은 이전 방향
  조건을 무효화한다. 실행기는 이동 후 실제 거리와 방향을 다시 읽는다.
- 실행 전 바닥의 내비게이션 경로를 구하고, 경로 각 구간을 실제 보스 캡슐 크기로
  검사한다. 길이 없거나 부분 경로만 있으면 접근을 강행하지 않는다.
- 일반 진입의 회전은 초당 최대 90도다. 공격 상태에 들어간 뒤의 회전 규칙은 바꾸지 않았다.
- 시간 초과·대상 변경·경로 실패는 중단 이유로 기록한다. 실패한 공격별로 3초간
  재선택 점수를 25%로 낮춘다. 왼손/오른손을 번갈아 실패해도 각각 기억한다.
- 650cm 안에서 이미 점수가 남은 공격 후보가 있다면 일반 접근의 점수를 0으로 만든다.
  현재 후보 배열은 기본 주먹이 접근보다 앞에서 평가되므로 기본 주먹의 실행 가능성을
  확인한 뒤 접근을 억제한다. 새 2연타를 추가할 때 후보 순서 의존성도 함께 제거해야 한다.
- 선택 거리, 진입 번호, 경과 시간, 진행 단계, 도착·중단 이유를 QA에 추가했다.
  `intent_arrived`는 명중이 아니라 위치 확보 후 공격 시작이 허용됐다는 뜻이다.

### 2단계 검증과 한계

실제 C++ 빌드 성공을 확인하고, 에디터 재시작 후 로드된 네이티브 GOAP에 거리·방향·
전후 경로 조건 96가지를 직접 넣어 결과를 확인했다. 총 24개 구조/계산 확인 항목을
통과했다. 보스 블루프린트 컴파일 오류·경고는 0개이고, 로그 분석 테스트는 8개다.
이 단계 당시에는 별도로 등록한 C++ Automation 테스트의 실행 완료 기록을 확보하지
못했다. 이후 아래 상태 전환 수정 단계에서 정상 실행하여 결과를 확보했다.

Arena의 RecastNavMesh와 NavBounds_BossArena 존재를 확인했다. MotionLab에는
내비게이션이 없다. 랩의 숫자키 실전 요청은 기존 직접 요청 경로를 사용하므로
새 진입 실행기를 거치지 않는다. 랩에서 자율 진입까지 확인하려면 후속 지원이 필요하다.

이번에도 PIE는 실행하지 않았다. 네이티브 계산 통과는 실제 경로 이동, 손 접촉,
발 미끄러짐 검증을 대신하지 않는다. 350cm 시작 상한 역시 아직 접촉 측정 전 값이다.
좌우 자리잡기는 새 GOAP 계산에 들어 있지만 새 진입 실행기에서는 아직 선택하지 않는다.
기존 공격 후 옆걸음 경로도 유지 중이며 통합 작업이 남았다.

## 2단계 후속 수정 — 상태 전환 전달값

정적 점검에서 새 진입 실행기의 오류를 찾았다. 블루프린트의 `TransitionBossState`는
`ExpectedState`가 현재 상태와 맞아야 `NewState`로 바꾼다. 기존 C++ 호출부는 두 값에
모두 목적 상태를 넣었다. 따라서 Ready에서 Position으로 전환하려고 할 때도
현재 상태가 Position이어야 한다고 검사해 거부되는 구조였다. 앞의 계산/연결 검사는
이 전달값을 검사하지 않았으므로 실행기의 정상 작동 근거로 사용할 수 없다.

- Ready → Position에는 예상 상태 Ready와 목적 상태 Position을 따로 전달한다.
- Position → Ready에는 예상 상태 Position과 목적 상태 Ready를 따로 전달한다.
- 함수 호출 후 실제 상태를 읽는다. 시작 전환이 거부되면 진입을 활성화하지 않으며,
  Ready 복귀가 거부되면 공격을 시작하지 않는다. 거부는 QA 중단 사유로 남긴다.
- 2026-10-06 KST 빌드 성공 후 에디터 재시작을 확인했다.
- 실제 보스 블루프린트 함수에 전달할 인자를 검사하는
  `Battle.GOAP.IntentTransitionParameters`와 기존 `Battle.GOAP.SelectedAttack`을
  AutomationController로 실행해 **2개 성공, 오류·경고 0개**를 확인했다.
- 별도 네이티브 계산 96가지·구조 검사 24개도 다시 통과했다.
- 전달값 검사는 액터를 생성하거나 함수를 실행해 전투를 관찰하는 검사가 아니다.
  실제 진입·공격·접촉은 여전히 사용자 플레이 확인이 필요하다.

## 3단계 준비 — 왼손 → 오른손 2연타

`AM_Boss_Left_Right`와 `DA_Attack_LeftRight`를 별도로 만들었다.

- 기존 3연타의 첫 두 주먹과 중간 연결 동작을 복사했다. 원본 3연타는 유지한다.
- 두 주먹의 디딤 이동·불꽃·손 판정 시점 6개를 그대로 유지한다.
- 세 번째 타격과 연결 동작을 제외하고 오른손 회수 동작으로 끝낸다.
- 각 타격 피해는 40, 재사용 대기시간은 4초, 시작 가중치는 20으로 준비했다.
  기존 첫 두 타격 템포는 유지한다. 마지막 회수 클립은 2.4배속, 전체 몽타주는
  기존과 같은 0.75배속을 전제로 한다.
- 전체 타이머는 약 5.067초, 마지막 Active 종료 뒤 후딜 타이머는 약 0.974초다.
  실제 반격 가능 횟수나 시각적 자연스러움을 보장하는 측정값은 아니다.
- 첫 네 모션 구간·첫 여섯 알림의 원본 일치, 타격 데이터 2개, 원본 보존,
  마지막 후딜 0.6~1.0초 범위를 저장된 에셋에서 다시 확인했다.
- **아직 실전 공격 목록에 넣지 않았으며 비활성 상태다.** 첫 타 후 연결 조건,
  쿨다운 배열, 모든 후보 계산 후 접근 억제, 계열 반복 감점과 랩 조작을 연결한 뒤
  활성화한다. 준비 스크립트는 기존 초안을 덮어쓰지 않고 재실행 시 검증한다.

## 남은 전체 범위

1. 현재 왼손·오른손의 중거리 의도 유지 구현을 실제 플레이 로그로 확인.
2. 제한 시간과 실패 감점이 반복 추격을 실제로 줄이는지 확인하고, 연속 실패 시
   짧은 관찰·다른 진입 행동으로 전환하는 정책 완성.
3. GOAP 좌우 자리잡기와 공격 후 선택을 새 실행 흐름에 통합. 과도한 후퇴를
   제한하고, 경로 변경·벽 근처에서 실제 이동 검증.
4. 준비한 왼손→오른손 2연타를 실전 목록·연결 조건·쿨다운에 통합하고 활성화.
   특수 3연타는 유지. 공격 연결 구간과 마지막 후딜 구분, 같은 공격 계열 반복 감점,
   상황에 맞는 휩쓸기·돌진 선택.
5. 선택 거리·시작 거리·실제 접촉 범위를 나누고 현재 모션의 물리적 도달성 확인.
   기본 펀치의 현재 66/87cm 디딤 이동을 근거 없이 늘리지 않는다.
6. 화면에 이번 의도·현재 행동·선택/중단 이유 표시. MotionLab 및 로그 연결.
7. 사용자가 플레이한 결과와 로그로 거리·후퇴·측면·밀착·벽 상황 확인.

전체 목표는 아직 진행 중이다. 이 파일과 1단계 컴파일 결과만으로
HFSM·Utility·GOAP 폴리싱이 완료됐다고 판단하지 않는다.
