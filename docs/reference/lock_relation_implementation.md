# 락온: 두 캐릭터 구도와 보스 기준 이동

## 이번 작업 범위

첨부한 락온 설명 가운데 **플레이어·보스를 함께 담는 화면 구도**와
**보스 기준 접근·후퇴·원형 좌우 이동**을 구현했다.
설명에 따른 Unreal 재구현이며 DS3의 원본 소스·동일한 내부 공식이라는 의미는 아니다.
650cm 거리, 수직 화각 43도는 현재 Battle 설정이다.

수정 자산: `/Game/BossArena/Player/Blueprints/BP_Player_Combat`.
현재 레벨에는 플레이어 배치 인스턴스가 없고 PlayerStart에서 생성된다.
네이티브 백업: `/Game/BossArena/Backup/BP_Player_Combat_PreLockRelation_20260929`.
기존 공격, 구르기, AI, 키 배치는 이 작업의 변경 대상이 아니다.

## 1. 이동을 어떻게 설명하면 되는가

`Move` 함수에서 타깃이 유효하면 플레이어 → 보스의 수평 방향을 구한다.
그 방향의 Yaw를 `MoveBasisYaw`에 저장하고 Forward/Right 벡터를 만든다.

- W/S: 보스 쪽 / 반대쪽.
- A/D: 보스 방향에 직각인 접선 방향. 플레이어가 움직일 때마다 방향을 다시 계산한다.
- 대각선: 두 방향을 합하고 CharacterMovement의 정상적인 입력·속도 제한을 사용한다.
- 비락온·달리기: 기존 카메라 ControlRotation의 Yaw를 쓴다.

카메라가 보스를 뒤늦게 따라와도 이동 방향 계산은 보스의 현재 위치를 쓴다.
캐릭터 회전 보간과 공격 방향 고정은 기존 별도 경로에 남아 있다.

### 원형 이동에서 바깥으로 밀리는 이유와 보정

접선 입력만 넣으면 가속·마찰 때문에 직전 프레임의 속도가 남아 원 바깥으로 밀린다.
첫 검증에서는 D 2초 후 500cm → 563.8cm로 벌어졌다.

따라서 A/D만 누르는 동안 시작 반지름 `OrbitRadius`를 저장하고:

```text
안쪽 입력 = Clamp((현재 거리 - 시작 반지름) × 0.02, -0.25, 0.25)
```

를 Forward 입력에 더한다. 위치를 강제로 고치거나 순간이동시키지 않는다.
W/S·대각선·비락온 이동에서는 보정을 끈다.
입력 완료 시 기존 LastMoveInput 초기화에 따라 다음 원형 이동은 새 반지름을 잡는다.

## 2. 구도를 어떻게 설명하면 되는가

`UpdateLockOnRotation`에서 다음 6점을 실제 viewport 좌표로 투영한다.

1. 플레이어 몸체 중심.
2. 보스 몸체 중심 + 캡슐 반높이 × 0.45.
3. 플레이어 캡슐 위·아래.
4. 보스 캡슐 위·아래.

몸체 기준점은 애니메이션의 숨쉬기·주먹 움직임에 따라 흔들리지 않는다.
가슴의 락온 표식은 기존 `spine_03` 소켓을 계속 사용한다.

화면 높이를 0=맨 위, 1=맨 아래로 보았을 때:

| 항목 | 목표/제약 |
|---|---|
| 플레이어 몸체 중심 | Y 0.70 |
| 보스 상체 기준점 | Y 0.36 |
| 머리 쪽 안전 여백 | Y ≥ 0.075 |
| 발 쪽 안전 여백 | Y ≤ 0.93 |
| 작은 상하 오차 무시 | 가중 오차 0.012 이내 |

상하 목표 오차는 플레이어 35%, 보스 65%로 합친다.
수직 화각으로 화면 오차를 각도 오차로 바꾸고 머리·발 제약에 맞게 제한한다.
기존 근접 편의 제한(-25~0도)과 RInterpTo 5로 보간한다.
따라서 목표 두 점이 항상 정확한 숫자에 고정되는 방식은 아니다. 안정성과 여백이 우선이다.

### 좌우로 겹치는 구도

락온 중 SpringArm SocketOffset.Y를 -55cm로 부드럽게 이동시켜 플레이어를 오른쪽에 둔다.
보스 상체 X 목표는 0.48이다. 거리·화각·측면 위치를 사용해 필요한 Yaw를 직접 계산한다.
이 계산은 원형 이동 중 보스 방향이 빠르게 변할 때도 따라갈 목표 각도를 제공한다.

카메라 길이와 화각을 거리마다 바꾸지 않는다.
측면 위치를 이동하는 구도 보정이며 줌 보정이 아니다.
달리기로 락온이 잠시 멈추면 측면 위치를 유지하고, 명시적인 락온 해제 때 중앙으로 복귀한다.
벽에 의한 SpringArm 충돌 축소는 기존대로 작동한다.

근접 접촉, 3m·5m·10m, 좌우 이동, W/S, 정지 중 카메라 안정성을 포함한다.
결과 파일: `Saved/VibeUE/lock-relation-evidence.json`.

실제 근접 화면과 오른쪽으로 돌아간 화면을 직접 확인했다.
첫 원형 이동 검사에서 드러난 관성 드리프트를 수정한 뒤 최종 검사를 통과했다.
최종 두 시나리오는 `verifiedCurrent=true`, 총 71개 검사 통과이다.
최종 Blueprint 컴파일 오류·경고 0, 두 최종 PIE 시나리오에서 Script Warning 없음.
작업 종료 시 PIE를 종료하고 배경 프레임 제한을 복원했다.

## 범위의 한계

몸체 전체와 바닥을 기준으로 구도를 잡는다. 모든 이펙트·무기 끝까지 항상 화면 안에
들어오게 하는 시스템은 아니다. 벽이 카메라를 밀거나 대상을 가리면 두 캐릭터의
전신을 항상 담는 것이 물리적으로 불가능할 수 있다.
여러 타깃 선택·전환이나 가림 후 락온 해제 유예시간은 이번 작업에 포함되지 않는다.
