# DS3 군다 원본 AI 추출 기록

조사일: 2026-10-04. **설치된 DS3 아카이브를 읽기 전용으로 분석한 결과**다. 공개된 모드 스크립트나 AI 함수 설명을 원본 행처럼 취급하지 않았다. 공식 배포본의 해시와 대조하지 못했으므로 `바닐라 인증`이 아니라 `이 PC의 Steam 설치본에서 추출`이라고 표현한다.

## 원본 데이터에서 확인한 흐름

```text
NpcThinkParam 511000/511100 → battleGoalId 511000
→ m40_00_00_00의 511000_battle.lua (분기 스크립트)
→ aicommon의 Gunda_battle.lua 또는 Gunda_HU_battle.lua
→ 거리·방향·체력·특수효과로 행동 가중치 부여
→ 쿨다운 적용 → 하위 Goal 실행 → 공격 후 별도 움직임
```

이는 DS3의 원본 AI 구조를 설명한다. **DS3가 GOAP를 사용한다는 증거는 아니다.** 여기서 `Goal`은 게임의 행동 단위이고, `Replaning()`도 해당 AI가 행동을 다시 고르는 함수명이다. Battle의 GOAP 설계와 이름만으로 동일시하지 않는다.

### 1. NPC/Think 파라미터

`Data0.bdt`의 해당 행 앞부분을 [Paramdex 필드 정의](https://github.com/soulsmods/Paramdex/tree/master/DS3/Defs)에 맞춰 읽고, 핵심 값은 원본 바이트와 다시 대조했다. 이름 대응은 [NpcParam 이름 목록](https://github.com/soulsmods/Paramdex/blob/master/DS3/Names/NpcParam.txt)을 사용했다.

| 필드 | 심판자 군다 `511000` | 영웅 군다 `511100` | 해석 주의 |
| --- | ---: | ---: | --- |
| `NpcParam.turnVellocity` | `70.0` | `70.0` | 필드 단위와 실제 화면 회전량은 아직 검증되지 않았다. `70°/초`라고 쓰지 않는다. |
| `NpcParam.hitHeight` | 약 `3.2` | 약 `3.2` | 몸/충돌 관련 파라미터이지 개별 공격의 손 판정이 아니다. |
| `NpcParam.hitRadius` | 약 `0.8` | 약 `0.8` | 같은 주의. |
| `NpcParam.Hp` | `1037` | `1451` | 행의 기본 HP다. 플레이 조건별 최종 HP와 구분한다. |
| `NpcThinkParam.logicId` | `10000` | `10000` | 두 행이 같다. |
| `NpcThinkParam.battleGoalId` | `511000` | `511000` | **두 군다가 같은 전투 Goal ID에서 시작한다.** 스크립트가 Think ID와 효과를 보고 분기한다. |
| `NpcThinkParam.nearDist / midDist / farDist / OutDist` | 모두 `0.0` | 모두 `0.0` | 거리 판단이 없다는 뜻이 아니다. 아래 스크립트에 직접 거리 분기가 있다. |

### 2. 분기 스크립트와 행동 선택

`511000_battle.lua`는 짧은 진입 스크립트다. 자신의 Think ID와 특수효과 `5404`를 확인해 기본 `GundaBattle` 또는 변형 상태의 `GundaHUBattle`로 넘긴다. **영웅 군다 `511100`용 완전히 별개의 최상위 스크립트를 찾은 것이 아니다.** 기본 전투 스크립트 안에서도 `511100`과 특수효과 `5020`을 검사해 후보와 가중치를 다르게 만든다.

기본 `GundaBattle`의 일반 분기에서 확인한 예시는 다음과 같다. 숫자는 **원본 스크립트의 행동 가중치**다. 쿨다운·조건·후속 선택을 거치므로 전체 전투의 실제 출현 확률이 아니다. `Act01`은 목표 쪽으로 접근한 뒤 공격 `3000` 계열을 실행한다. `Act02`도 접근한 뒤 공격 `3002`를 실행한다. 따라서 멀리서 두 후보 중 하나를 고른다고 해도 `75% 대시 기술`이라고 읽으면 틀린다.

| 조건, 기본 분기 | 주요 가중치 | 의미 |
| --- | --- | --- |
| 전투 진입 후 `GetNumber(0)==0` | `Act21=10` | 먼저 접근 행동을 실행하고 내부 숫자를 바꾼다. |
| 플레이어가 뒤쪽, 지정 범위 안 | `Act06=70`, `Act20=30` | 뒤쪽 대응 공격과 **턴 동작**이 함께 후보가 된다. |
| 플레이어가 뒤쪽, 그 범위 밖 | `Act20=10` | 몸을 돌리는 동작을 선택한다. |
| 플레이어가 특정 오른쪽 측면 | `Act04=55`, `Act05=45` | 측면에 맞는 다른 공격 후보를 연다. |
| 플레이어가 특정 왼쪽 측면 | `Act04=25`, `Act05=35`, `Act08=40` | 반대쪽 측면은 분포가 다르다. |
| 거리 `>=10` | `Act01=75`, `Act02=25` | 원거리에도 접근을 포함한 두 공격 루트가 남는다. |
| 거리 `>=8` 및 `<10` | `Act01=30`, `Act02=55`, `Act09=15` | 멀어도 한 행동으로 고정하지 않는다. |
| 거리 `>=3` 및 `<8` | `Act04=10`, `Act05=10`, `Act09=75` | 중거리에서 주력 후보가 바뀐다. |
| 거리 `>=1.5` 및 `<3` | `Act04=10`, `Act05=10`, `Act07=35`, `Act08=10`, `Act09=35` | 가까운 거리에도 다양한 후보가 남는다. |

원본 AI 거리값 `1.5/3/8/10`을 UE의 cm나 Crunch 공격 거리로 그대로 변환하지 않는다. 군다의 몸 반지름을 빼서 접근/타격 거리를 계산하는 곳도 있다. 예를 들어 `Act01`은 `18 - GetMapHitRadius(TARGET_SELF)`를 접근 기준으로 사용한다. **“플레이어까지 거리”와 “실제 때릴 수 있는 자리”를 분리**한 점이 Crunch에 중요하다.

선택 전에는 `SetCoolTime`이 행동 가중치를 다시 조정한다. 예를 들어 공격 `3000`에 `10`, 공격 `3002`에 `8`, 공격 `3010`에 `16`을 전달한다. 이 인자를 스크립트상 쿨다운 설정값으로 기록하되, 각각을 검증 없이 포트폴리오의 `초` 단위로 인용하지 않는다. 특히 `511000`일 때 `Act06`을 `0`으로 막고 `Act07`의 가중치를 `0.2`배 한 뒤 별도의 쿨다운을 거는 분기가 있다. 조건과 쿨다운이 표의 초기 가중치를 다시 바꾼다.

### 3. 회전, 연속공격, 살아 있는 움직임

- `Act20`은 `GOAL_COMMON_Turn`을 호출하고 `GetRandam_Int(15, 90)`을 인자로 준다. `15~90`은 **턴 행동의 인자**이지 `기본 회전 속도`가 아니다. 이 함수의 정확한 인자 의미와 실제 애니메이션 회전량은 별도 검증이 필요하다.
- 공격 실행에는 `GOAL_COMMON_AttackTunableSpin`, `ComboAttackTunableSpin`, `ComboRepeat`, `ComboFinal` 같은 서로 다른 하위 Goal이 있다. `Act01`은 자체 난수에 따라 단발 또는 여러 연결 공격을 고른다. **행동 선택의 다양성**과 **선택 후 콤보 연결**이 분리되어 있다.
- 공격 뒤에는 `AfterAttackAct`가 호출된다. 기본 군다는 가까운 측면 상황이나 거리에 따라 `GOAL_COMMON_SidewayMove`를 넣는다. 즉 **공격이 끝난 뒤 멍하니 멈추기보다 자리를 다시 잡는 단계**가 원본에 있다.
- 변형 상태의 `GundaHUBattle`은 공격 후 `GOAL_COMMON_AfterAttackAct`에 앞/뒤·옆 움직임의 가중치를 전달한다. 거리 구간에 따라 `Odds_BackAndSide_AAA`가 `20/30/30/10`, 가까울 때 `Odds_Back_AAA`가 `10`으로 바뀐다. 이 값도 실제 이동 빈도와 같다고 단정하지 않는다.
- `Goal.Interrupt`에서는 특수효과, 대상의 거리/각도 이탈, 피해, 아이템 사용 등으로 현재 하위 Goal을 비우거나 `Replaning()`을 호출한다. 모든 공격을 언제나 끝까지 취소할 수 있다는 뜻은 아니다. 실제 취소 허용 시점은 Goal과 모션 이벤트까지 확인해야 한다.

### 4. 실제 애니메이션 이벤트: `c5110.tae`

원본 `Data3.bdt`에서 `/chr/c5110.anibnd.dcx`를 선택적으로 추출하고, 그 안의 `c5110.tae`를 [SoulsFormats의 TAE3 판독기](https://github.com/JKAnderson/SoulsFormats/tree/master/SoulsFormats/Formats/TAE3)로 열었다. **133개 애니메이션 항목**이 있고, 위 AI의 `Act01`이 호출하는 공격 `3000`에도 Type 224 이벤트가 여러 구간으로 나뉘어 있다.

| `3000` 애니메이션 시간 구간 | Type 224의 원본 숫자 |
| --- | ---: |
| `0.000–0.167` | `90` |
| `0.167–0.367` | `180` |
| `0.367–0.500` | `0` |
| `0.500–0.867` | `360` |
| `0.867–1.000` | `0` |
| `1.000–1.233` | `240` |
| `1.233–1.533` | `10` |
| `1.533–2.733` | `0` |
| `2.733–3.033` | `120` |
| `3.033–4.000` | `0` |

[Souls Modding의 TAE 설명](https://www.soulsmodding.com/doku.php?id=format:tae)은 Type 224를 해당 구간의 회전속도 변경으로 설명하지만 단위는 미확정으로 둔다. 따라서 이 표는 **이 모션에 회전 관련 값이 시간별로 달라진다는 원본 증거**이지, `360°/초로 돈다` 또는 `타격 중 정확히 몇 도 추적한다`는 측정이 아니다. 다른 공격 `3002`에도 Type 224가 있으며 일부 구간이 겹쳐 보여 단순히 한 값으로 환산하면 안 된다. 타격 판정 시작/끝과 플레이어가 보는 주먹 접촉 프레임은 이 이벤트 표만으로 확정하지 않는다.

## Crunch에 옮길 설계 판단

원작 숫자를 그대로 복사할 필요는 없다. 포트폴리오에서 보여줘야 할 **원리와 구현 이유**는 다음처럼 명확하다.

1. **Utility AI:** 거리·앞/옆/뒤·반복 방지에 따라 복수 후보의 가중치를 바꾼다. 먼 거리도 `달려 접근`, `준비 후 돌진`, `관찰/재배치`가 함께 가능하게 둔다.
2. **HFSM:** 고른 공격의 준비·Commit·타격·후딜을 지킨다. 원본의 `TunableSpin`을 `끝까지 추적 가능`으로 오해하지 않고, Crunch에서는 공격별 회전 허용을 실제 모션과 맞춰 측정한다.
3. **움직임:** 공격 후에도 때때로 측면 이동이나 짧은 후퇴를 선택한다. 플레이어가 뒤를 잡으면 즉시 180° 스냅하지 않고 턴 동작 후보를 연다.
4. **GOAP:** DS3 `Goal`의 존재를 GOAP 증거로 쓰지 않는다. Crunch의 GOAP는 `공격할 위치 확보 → 방향 정렬 → Utility가 공격 선택` 같은 **짧은 목적 기반 계획**으로 별도 설명한다.
